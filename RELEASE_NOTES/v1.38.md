# Investigation & Resolution Report: Pack Import Failure Without `pytorch_lightning` (Issue #5)

This document explains why missing **`pytorch_lightning`** caused ComfyUI to fail loading **the entire** `ComfyUI-NunchakuFluxLoraStacker` custom-node pack (not only CCSR), what was changed in **v1.38**, and how users/ComfyUI-Manager pick up the fix.

**Related issue:** [Issue #5](https://github.com/ussoewwin/ComfyUI-NunchakuFluxLoraStacker/issues/5)

---

## 1. Problem Description

On environments such as **ComfyUI-Easy-Install**, startup logged:

```text
[WARNING] Cannot import ...\ComfyUI-NunchakuFluxLoraStacker module for custom nodes:
No module named 'pytorch_lightning'
```

After that warning, **no nodes from this pack** appeared in the UI—FLUX LoRA loaders, Florence-2, Resolution Selector, and CCSR were all unavailable. Users who never use CCSR still lost the whole extension.

---

## 2. Root Cause Analysis

### Cause A: Eager top-level import of CCSR

Root `__init__.py` imports CCSR at pack load time:

```python
from .nodes.CCSR import NODE_CLASS_MAPPINGS as CCSR_NODES, NODE_DISPLAY_NAME_MAPPINGS as CCSR_NAMES
```

ComfyUI loads a custom node by executing that module. If **any** top-level import raises, ComfyUI discards the **whole** pack.

### Cause B: CCSR import chain requires `pytorch_lightning`

The CCSR subtree (from [kijai/ComfyUI-CCSR](https://github.com/kijai/ComfyUI-CCSR)) imports Lightning early, for example:

```text
nodes/CCSR/… → ddpm_ccsr_stage1.py → import pytorch_lightning as pl
```

If `pytorch_lightning` is not installed in the ComfyUI venv, that import raises `ModuleNotFoundError`.

### Cause C: Dependencies were not declared at pack root

`nodes/CCSR/requirements.txt` already listed CCSR deps (including `pytorch-lightning>=2.2.1`), but the **root** `requirements.txt` used by ComfyUI-Manager / Easy-Install did **not**. There was also **no** root `install.py` hook to install them on Manager install/update.

Environments that already had Lightning (or had installed CCSR deps manually) never showed the bug—so it was easy to miss until Issue #5.

---

## 3. What Changed in v1.38

### 3.1 Root `requirements.txt`

Added the CCSR dependency block (aligned with upstream CCSR / `nodes/CCSR/requirements.txt`):

```text
# CCSR upscaler (nodes/CCSR) — required at pack import time
# Without these, ComfyUI fails to load the entire custom node pack (see issue #5)
taming-transformers
omegaconf
einops
pytorch-lightning>=2.2.1
open-clip-torch>=2.23.0
```

### 3.2 New `install.py` (ComfyUI-Manager hook)

Added root `install.py` so Manager **install / update** runs:

```text
python -m pip install -r requirements.txt
```

in the active ComfyUI interpreter—ensuring Lightning and the other CCSR packages are present after Manager operations.

---

## 4. Files Touched

| Path | Change |
|------|--------|
| `requirements.txt` | Add CCSR packages including `pytorch-lightning>=2.2.1` |
| `install.py` | **New** — pip install `-r requirements.txt` for Manager |
| `md/CHANGELOG.md` / `zhmd/CHANGELOG.md` | v1.38 summary + release URL |

---

## 5. How to Apply

1. **Update this custom node** (git pull / ComfyUI-Manager Update).
2. If Manager does not run `install.py` automatically, from the ComfyUI Python environment:

```bash
python -m pip install -r requirements.txt
```

3. **Fully restart ComfyUI** and confirm the pack loads without the `pytorch_lightning` warning.

Existing installs that already have Lightning need no extra action beyond updating the repo files.

---

## 6. Notes

- **v1.38** is a dependency / install-path fix. CCSR node behaviour itself is unchanged from the v1.35 integration.
- Publishing / tagging this release does **not** require touching Comfy Registry version gates beyond normal pack versioning when you bump `pyproject.toml` / `__version__` separately.
